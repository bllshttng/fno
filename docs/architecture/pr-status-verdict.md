# PR status verdict: the narrative behind `fno do pr status`

Since the 2026-09-25 port, the reader, verdict, failure detail, composer, coalescing cache and wait/logs commands are Rust. They live in `crates/fno-agents/src/pr_status.rs` and `pr_status/{cache,compose,reviews,seams,wait,logs}.rs`. Python reaches them through the `authorized-merge` status door (`status-read`, `status-wait`, `status-logs`, `status-ci`, `status-rerun`). `cli/src/fno/pr/cli.py` forwards. The offline row read the board renders from is `pr_status::cache::newest_row`, called by `backlog/projections.rs`. This file holds the reasoning the code used to restate. The tree number and the reasoning both survive.

## `verdict_for`: pure verdict computation

Returns `(verdict, exit_code, counts)`. Classifies only the latest run per check name so a superseded CANCELLED run (left in the rollup by a force/amend push) no longer yields a false red.

`counts["total"]` is the deduped count over the WHOLE rollup, which carries two different kinds of row: GitHub check-runs (the `name` key, produced by Actions and Checks-API apps) and commit StatusContexts (the `context` key, posted to the statuses endpoint). `counts["check_runs"]` and `counts["statuses"]` split that total, because a reader who compares `total` against `gh api .../check-runs` sees a phantom gap otherwise: that endpoint never returns statuses. Measured 2026-08-20 - the tally said 15, the check-runs endpoint named 13 jobs, and the gap was fno's own statuses. The coverage-context filter (`without_coverage_statuses`) feeds this function, so the two review-coverage StatusContexts are already absent from every count here. The two sub-counts need not sum to `total`: a rollup row carrying neither key is counted in neither (it is also never deduped).

`counts["fail_check_runs"]` and `counts["fail_statuses"]` split the fail bucket the same way, and they are what lets a caller name a red honestly. The VERDICT deliberately does not split: a failing StatusContext is a real red (`stacked-base-guard` is one), so it must never read green. What the split fixes is the ATTRIBUTION - the red-kind word rides the preview payload (see `ready is the preview verdict`).

`counts["unsettled"]` counts latest runs with NO settled marker (an absent result: cancelled, stale, still running), and `settled` is derived from it positively elsewhere - never from the absence of a pending run. `counts["unsettled_fail"]` narrows that positive count to rows that also classify as failures, so callers can distinguish a taken-away run from a concluded failure without inferring either outcome from an absence.

When NO entry is a real check-run (the `name` key, from GitHub Actions and Checks-API apps), a would-be-green tally is refused. A PR whose only entries are fno's own self-published StatusContexts has had no real CI run. That covers a head conflicting at push time: no `pull_request` workflow ever started on it. fno's own StatusContexts (review-coverage, stacked-base-guard) still post and can all pass. An all-`context` rollup can therefore read as green with no CI having run at all. A fail or pending StatusContext is still a real, actionable signal and stays red/pending.

Known tradeoff, not footnote's own blast radius: a repo whose ONLY real CI still rides the legacy commit-status API (no GitHub Actions, no Checks-API app) would never clear this and would hold forever under `require_checks_pass` (unknown holds, never fails - see the checks arm of `crates/fno-agents/src/authorized_merge.rs`). footnote's own workflows (guards.yml et al.) are all Actions/CheckRuns, so this repo never hits it; a fork that genuinely needs status-only CI as its sole signal should route around this via `require_checks_pass=false`.

Cancelled check runs whose failure annotations say they exceeded a `timeout-minutes` cap are relabeled `timed_out`; a missing or unreadable annotation keeps the run `cancelled`.

## `run_status`: the authoritative read

Prints a one-line JSON verdict for a PR. The exit code is ALWAYS the CI verdict's code (0/1/2/3/4/127). Exit 4 means read failed: a fetch error or a crashed reader, never a red PR, and its stdout still carries one JSON line. The review fields are additive and advisory, and an unresolved optional finding on a green PR still exits 0. `ready` is the authorized-merge preview verdict. Status asks the one decision the merge command runs and reads `ready_blockers` off the receipt. The receipt itself rides as `merge_decision`. A PR that reads `ready: true` here is a PR `fno do pr merge` authorizes. Only one of the two commands computes, so they can no longer answer opposite ways. The facts this read already paid for ride the preview payload. Those are the verdict, the red-kind word, rerun recovery, the unresolved optional count, and the GitHub merge-state blockers. The owner never spawns a second status read for them. An unreachable owner fails closed as `merge_decision_unknown`, never ready. A caller branching on the exit code is untouched. `review_reader` is injectable for tests, and defaults to the real time-boxed read.

The review and coverage reads are computed AFTER the authoritative CI verdict so a slow/failed read can never delay or corrupt it, and every one of them degrades to "unknown"/None on failure: the verdict plus exit code stay authoritative. The rerun-recovery probe (`rerun_recovery`) rides the same discipline: a green read gains the `rerun_recovered` / `recovered_failures` keys, present iff the probe ran, and the merge gate's flake hold consumes the same fact.

## `verdict_line`: slot ordering

The conclusion goes LAST and every slot before it is a fact, so a reader who stops early holds facts and no verdict - never a verdict about a different question. Each of the four misreadings this retires read a subset of the JSON and answered confidently anyway: a state slot that is always present cannot be omitted by the reader either, `verdict` and `settled` now sit adjacent, a head mismatch carries both commits in one line, and the mergeable slot states its own meaning instead of handing the reader a word to interpret. Slots are fixed, always present, in one order; a wrong value renders LOUD (capitals, parentheticals) so scanning for trouble is a real reading strategy. Keyed on the payload dict, never on run_status locals: `_cache._serve` degrades a stale row IN PLACE, so a payload-keyed renderer tells the degraded truth with no second code path.

On a red, live PR the optional `history:` slot reports a cancelled or timed-out check's branch history. It names how many runs passed on the branch, how many were cancelled by a newer push, and, when available, compares this head's duration with the median of recent passing PR runs of the same workflow; main is not the baseline because PR-only jobs do not run there. The facts are reused across reads of one head by GitHub job id, so a cache refresh does not re-read completed jobs.

## Payload-keyed note renderers

`coverage_recompute_note`, `failures_note`, and `rerun_recovery_note` are shared by the live read and the cache serve, so a degraded reason, a failure detail, or a rerun warning reaches every terminal rather than only the one session whose read produced the row. The bare success note stays silent: it adds nothing the coverage line does not already say, and a prefix that fires on every first poll trains a reader to skip the line where a reason appears. `failures_note` reads the PAYLOAD, never run_status locals, so every watcher sharing the row sees why the PR is red without any of them re-reading the log.

## `ready` is the preview verdict

`ready` and `ready_blockers` are the authorized-merge preview's receipt (`crates/fno-agents/src/authorized_merge.rs`, `Effect::Preview`). The ported gate probes live in `merge_gates.rs`. The merge command's first-refusal chain and the preview's collect-all walk share one ordered gate list. A blocker code is the same word whichever command names it. The effect path stops at the first blocker. The preview collects everything it can evaluate, which is what a lead needs to plan a merge order without attempting merges.

The codes keep the status vocabulary readers key on. Those include `review_in_flight`, `review_coverage_uncovered`, `dispatch_hold`, `rerun_recovered_green`, `optional_reviews_unresolved`, `ci_red`, `github_blocked`, `ci_base_stale`, `visual_approval`, and `merge_slot_held`. They add the merge-side refusals status never saw. Those are `pr_terminal`, `auto_merge_disabled`, `per_run_no_merge`, `node_unbound`, `head_not_covered`, `head_moved`, `stacked_base`, `red_merge_result`, `base_overlap`, `stub_manifest_unreconciled`, and `plan_fidelity_refused`. A red is still named for its KIND (`ci_cancelled_retrigger`, `commit_status_red`). The gate derives the word from the counts facts status supplies, so the split survives the port.

`ci_base_stale` and `merge_slot_held` were the gate's originals. They existed only inside the merge decision. A stale PR behind a held slot read ready, and the queue's truth arrived one refusal at a time. The slot gate in preview is read-only. A stale PR whose merge result cannot verify reads `ci_base_stale` with a free slot, and the slot is never taken, renewed, or released. A proven merge, or a self-held slot whose one retest is spent, reads none. A TERMINAL PR reads exactly `["pr_terminal"]`. The gate guards a would-merge, and a merged or closed PR has none left.

`unknown` coverage blocks and is named as its own blocker (`review_coverage_unknown`). An unreadable merge decision blocks as `merge_decision_unknown`. Required gates fail closed: a reader that cannot answer never answers ready. Optional reviews are the one exception: an unreadable optional-review count prints a warning and holds nothing, because the reviews are optional.

One gate depends on the project's paint surface. `merge.visual_paint_paths` lists render-surface paths. A PR whose changed files touch a listed path carries `visual_approval`. Two things clear the hold. One is an answered question page that names the PR and its head sha. The other is a role row. It records the user's chat approval of the PR at its head, cites the answered board page, or attests the identifier-only shape. That attestation says the paint edits rename identifiers only and every rendered string stays byte-identical. That shape has no shots, and a look judges nothing. All bind to the head the attestation names. A push after the look holds again, so a paint PR never merges unlooked unless the attested shape is the identifier-only one. The gate files the question itself, once per head, and passes the node's mux shots (`<node>-*.png` in the project's vault `mux` folder) as `--image`. With no shots it files nothing and names the capture step. An unreadable changed-file list reads `visual_paint_paths_unknown` rather than releasing the hold. Some checkouts have no key in any config tier. When such a checkout carries `crates/fno/src/client`, it arms a built-in list. The list holds the mux client and its render modules (theme, splash, chrome, the overlays, the web pages). `BUILTIN_VISUAL_PAINT_PATHS` in `agents_config.rs` names each file. Every other project stays disarmed until it names a paint surface. An explicit `visual_paint_paths = []` disarms the gate. The hold also stops the terminal `finalize` from arming GitHub's native auto-merge, because the arm walks the same decision chain.

The hold also holds CI. While `visual_approval` stands at a head, the daemon's `look_hold` arm cancels every run on it but `rust-ci.yml`, which carries the shots. The answer at that head reruns them. See [pr-heal](pr-heal.md#the-look-hold).

The Python ready conjunction is retired (`_ready_blockers`, the waiver overlay, the posture and rerun appends). The waiver overlay runs inside the coverage gate the preview shells (`fno do pr coverage-check`). A waived PR exits 0 at the gate, and no status copy of the overlay can drift from it.

## The GitHub merge state conjunct

`mergeable` answers "does it conflict". `mergeable_state` answers "will GitHub merge it". A ruleset, a branch-protection rule, or a required review holds a merge with no check going red. Every such gate at the GitHub layer was invisible to this verdict. The PR read `ready: true`, and the refusal landed only at merge time, after the worker reported success. Measured 2026-09-18 on PR 2210: `ready true, ready_blockers []` beside `mergeable_state: blocked` under ruleset 21074865 requiring the `smoke` context.

`fetch_pr_rest` carries `mergeStateStatus` and `baseRefName`. `_github_merge_blockers` spreads them to the `status-merge-blocker` op on the `authorized-merge` door (`crates/fno-agents/src/pr_status_facts.rs`), which owns the mapping. An absent `mergeStateStatus` (an old stub, a degraded fetch) asks nothing, like `mergeable=None`. An unreadable Rust owner fails closed as `github_merge_state_unknown`. The mapping: `clean`/`has_hooks`/`unstable`/`dirty`/`unknown`/null add nothing by themselves. `dirty` is covered by the `mergeable` field's own word: `CONFLICTING` maps to `not_mergeable_conflicting`, a still-computing null maps to `not_mergeable_unknown`, `MERGEABLE` adds nothing, and an absent key adds nothing. `behind` maps to `github_behind`, `draft` to `github_draft`, `blocked` to `github_blocked`. A state GitHub adds later fail-closes as `github_merge_state_<value>`. On `blocked` only, the op reads `gh api repos/{owner}/{repo}/rules/branches/<base>` in the checkout. Every context of a `required_status_checks` rule whose rollup row is absent or not SUCCESS/NEUTRAL/SKIPPED lands in `missing_required_checks`. When the PR's own reviewDecision does not read APPROVED, a `pull_request` rule with `required_approving_review_count > 0` adds `required_review`. A rules read that fails or names no unsatisfied rule answers `missing_required_checks: null`, with the reason in `source`. The blocker is never dropped. `verdict_line` renders the list as `(missing: a, b)`. Both the merge effect and the preview hold on these words. Status passes the computed blockers into the preview payload, so the gate and the readout share one answer.

## The failure-cause order

`_failures.first_error` is a transport. The logic is the `status-failure-cause` op in `pr_status_facts.rs`. The block is scoped in order of strength. When the job's `steps[]` are in hand, the failed step's `[started_at, completed_at]` window scopes it. That window is the one scope that survives a plain Actions job, whose group line spells `Run <command>`, never the step's name. Otherwise the block starts after the last `##[group]<step>` / `::group::<step>` / `=== <step> ===` marker before the step-failed line. With no marker, the whole log up to that line is the block. The old Python matched only `::group::`. Downloaded GitHub logs spell the marker `##[group]`. The block start therefore never matched in production, and the scan ran from line 1 of the whole job log. That is how a passing test's deliberate stderr was named as the cause. The real panic sat two thousand lines down. Within the block the order is cargo first. `heal::cargo_test_names` names the FAILED test, then its `thread '<name>' panicked at file:line` line and message. Pytest comes next: `heal::pytest_nodeids` names the FAILED node id, joined with its contiguous `E` lines. Note-prefixed `E` lines sink last. Then comes the earliest line matching the ported `_ERROR_PATTERNS`, then the block tail. The cause caps at 480 characters and announces the cut.

## Runs that fail before minting a job

When GitHub cannot parse a workflow file, the run completes as `failure` with zero jobs. A run with no jobs mints no check run. A reader that only reads check runs and legacy statuses skips it. That reader can call the commit green while the one broken workflow is red. `fetch_pr_rest` therefore reads the `actions/runs?head_sha=<sha>` listing it already holds. A run with no check-run link qualifies by three facts. It is `completed` with conclusion `failure` or `startup_failure`. Its jobs read answers zero. Then the rollup gains a failure row named by the run's workflow path. The newest run per workflow path wins, so a newer green run of the same workflow supersedes an older zero-job failure. The rule lives once, in Rust (`pr_status_facts::zero_job_failures` behind the `status-zero-job-runs` op). The Python row is transport only, and a failed read is `(None, reason)`, the module's loud-failure contract. The same rows reach pr-watch and pr-push through `pr_push::read_checks_rows`, and the lead and operator-notice main-CI readers reduce them with the stop gate's truth table.

## `cached_status`: the coalescing chokepoint

Every cached caller enters here: `fno do pr status`, `fno do pr wait` ticks, the lead board gate read, `authorized_merge`, and the nudge ladder. They share one row per key under a per-key flock. The key is minted by the authorized-merge owner's `status-cache-key` op. It hashes every fact the decision reads. Those are the head, the PR state, the dispatch-hold word, the live merge-slot rows, the repo's authority config, and the review evidence at the head. A hold release, a slot move, a merge, or a fresh attestation rekeys the row. The next read is live instead of serving yesterday's verdict inside the TTL. An unreachable owner falls back to the head-only key, and the cache keeps working with the old staleness window. The GraphQL quota is per-USER. The REST secondary limit counts request rate, so transport saves nobody. Only collapsing N reads into one helps. The head is part of the key because a verdict is a fact about one commit. A row cached for head A must never answer for head B. Head B's check set can still be empty. This is the operator's org zero-checks fail-open.

One cheap REST read buys the current head on every call. The expensive reads collapse to one per TTL: check-runs, the runs listing, combined status, logs, reviews, coverage. Transient failures are NOT cached. A loud error must reach every caller, never be replayed from disk. A refused read writes nothing.

### Why no row is served without the head read

Outside a live fleet backoff, the head read fires on every call. A push is therefore noticed on the very next tick. `_serve` never fabricates. A row with no output reads as a miss. A corrupt exit code also reads as a miss. A concurrent fno install can write a different schema. The served line carries the time and the head the verdict was computed at. That is `cached_at`, `cached_age_seconds`, and `head`. `cached: true` alone is decorative. It says the answer is second-hand but gives no way to judge whether the staleness matters, so every consumer ignored it. There is deliberately no `cached_head`. It was a verbatim copy of `head` under a second name. One fact, two places to drift apart.

### The backoff pre-check

Whether GitHub is refusing the machine is the fleet budget ledger's question, not this cache's. `_quota.backoff_live` reads the machine-wide ledger. Inside a live backoff, the head read itself is a held call. Every waiter's tick then short-circuits to the newest cached row. A fixed-interval retry is exactly what sustains a refusal. The row serves in the mode the normal path chooses. Fresh serves VERBATIM. A loud first-read error row keeps its exit 4. Degrading it softens a refusal into an "unknown" nobody asked for. Stale serves degraded: `verdict: unknown`, `settled: false`, and the failure diagnosis dropped. `ready_blockers` collapses to `["status_stale"]`. A stale row's gate answers are history. Replaying one beside an unreadable read names a hold the world already released. A payload that declares the check set unreadable must not also print per-check notes. Those notes then assert a diagnosis the serve just called unverifiable. This is the fail-closed stale serve, the operator's org. A watcher grepping settled:true waits out the window instead of waking on unverifiable green. With no readable head at all, the newest existing row serves degraded the same way. With no row, the loud live read decides. `--refresh` is the sanctioned escape and a MANUAL command. No row is served. The live read runs. It defeats the coalescing this module exists to do, so never put it in a watcher loop. It was built because a lead who distrusted a cached verdict had no option except raw `gh api`. `--refresh` also clears the spend-note budget global. A note must never name a ledger probe the read did not make.

### The miss lock

Synchronized pollers queue under the per-key flock. The watcher fleet sleeps 60s in near-lockstep, and the TTL is 60s, so they all miss together. The winner refreshes while the losers wait. The losers then re-read the now-fresh row and serve it. That is the collapse the module exists to deliver. Without the lock, every one of them runs the full read. The row is replaced wholesale on success. A new head sha never merges into an old verdict. Superseded heads' rows and locks are pruned right there. A served verdict must describe the current head.

### Reuse across reads of one head

The row being refreshed rides back into `run_status` as `prior`. Its `failures` entries key on GitHub job ids. GitHub mints a new job id per attempt. A completed job's log never changes. When the rollup names the same job id, its entry is replayed. A re-run that replaced the job fetches only the new job's log. Reuse never crosses heads. The key that carries the row includes the sha. A new head has no prior row, and its first read fetches everything. On green, a prior payload at the same head and check count replays the rerun facts. Those facts are `rerun_recovered` and `recovered_failures`. A recovery is history of one head. A new attempt cannot fail and then recover between two reads without the verdict or the check count changing first. `rerun_recovery` accepts the workflow-run listing `fetch_pr_rest` already read for the workflow names. A miss therefore reads it once, not twice.

Row guards keep the numbers alive inside a shared file. `json.loads` accepts a bare NaN or Infinity. A row carrying `"ts": Infinity` parses cleanly and survives `float()`. Every numeric read therefore goes through `finite_or_zero`. That guard once lived on one of two reachable paths, under a docstring claiming it covered both. The board then crashed on the second path. Finite is necessary and NOT sufficient. `1e18` is perfectly finite and still raises out of `time.gmtime`. The timestamp conversion is guarded where it happens. `finite_or_zero` must not widen into a timestamp validator it is not.

## Conditional reads

Every plain REST GET through the status door (`RealGhProbe::run_gh`, `crates/fno-agents/src/pr_status_facts.rs`) is conditional. `crates/fno-agents/src/gh_etag.rs` owns the rule and the row store. Eligible shapes are exactly two tokens, `api` plus a path under `repos/`. Writes, flags, `graphql`, `actions/jobs/{id}/logs`, and check-run pages past the first stay plain. When a row exists, the door sends `gh api -i <path>` with `If-None-Match: <stored etag>`. GitHub answers 304 and the door serves the stored body without spending core quota. The request still counts against the secondary rate limit. Only the shared poller lowers that, as the next paragraph says. Rows live at `<state_dir>/cache/gh-facts/etag/<sha256-of-path>.json` (override with `FNO_GH_FACTS_DIR`), holding `{etag, body, ts}`. A row older than 24h, corrupt, or missing is a miss, never an error: the read goes out plain, and the next 200 reseeds it. `gh` exits 1 on a 304, so the door parses the `HTTP/2.0` status line from stdout and ignores the exit code. The `pr status` and `pr wait` spend notes name 304s: `, {n} served 304` appears once the process has served one.

The stop-hook loop-check reaches the same door. In `cli/src/fno/pr/_internal_gh.py`, `_rest_runner` sends each plain `gh api repos/...` GET from the real process runner to the `status-rest-get` op of the `authorized-merge` command, which calls `run_gh`. Python holds no copy of the rule. The op answers `eligible: false` for a path the door skips, and the adapter then runs that read itself. An unreachable `fno-agents` binary does the same. The op judges the caller's origin against the fleet budget once, by the rule of the `admit` op. An agent is held. An attended user never is. A delegated read therefore skips the adapter's own `admit` call, and the spawn skips the origin-blind admission inside `bounded_read`. A runner injected by a test never reaches the door.

With `store.remote_url` set, one host also reads GitHub for the others. `cached_status` asks `gh_poller::follow` after the local TTL serve misses and before any network read. The `status` command skips that step, because its readers act on `ready` and the local merge gates. A shared row from the host that holds the `gh-budget:poller` lease, under two TTLs old on the store clock, serves with zero gh calls. It keeps the GitHub facts and drops the publisher's local gate fields. `live_through` publishes each row it writes while this host holds the lease. The row keeps its true age, so `cached_age_seconds` never reports a shared row as fresh. The design is in [One GitHub poller](multiplayer.md#one-github-poller).
