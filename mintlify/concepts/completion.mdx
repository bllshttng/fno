---
title: "How completion works"
description: "Distinguish an open PR, green checks, completed review, and a merged change."
---

An agent saying “done” does not prove that its change passed. fno reads evidence outside the agent's own summary.

For a walkthrough, see [review and ship](/guides/review-and-ship). For policy settings, see [configuration](/reference/configuration).

## Read the evidence in order

| Evidence | What it tells you | What remains to check |
| --- | --- | --- |
| PR URL | A proposal exists | Current head, diff, checks and review |
| Green CI | Checks passed for that head | Review and merge requirements |
| Review completed | The configured review policy ran | Blocking findings and merge readiness |
| Ready to merge | Current delivery gates permit merging | Merge authority |
| Merged PR | Changes reached the base branch | Any separate release or deployment |

Checks belong to a commit. Pushing a fix changes the head and can require new checks or review evidence.

## The target finish line

A target normally works toward an open PR, green CI, and satisfied review requirements. Your project's configuration controls those requirements.

Review has a configured round limit. Reaching that limit can leave findings documented in the PR rather than resolved in code.

Read the review findings themselves. “Reviewed” does not always mean “every suggested improvement was implemented.”

## CI is one reading

The CLI reference describes the [PR status command](/reference/cli#pull-request-status). Its green CI verdict alone does not establish completed review.

A pending check is unfinished work, not a failed check. An unknown or failed read is missing evidence, not a pass.

## Merging is a separate action

Automatic merging is disabled by default. A project can enable it, so check the [effective policy](/reference/configuration#automatic-merging) before a run.

A merged PR does not prove a website is deployed or a package is published. Those deliveries need their own evidence.
