The backlog stores tasks and their relationships. A task record is called a node. Its status and live ownership are separate facts.

## Before you begin

Install fno through the [quickstart](/quickstart) and run commands from your project repository.

The [CLI reference](/reference/cli#backlog) lists the inspection and editing doors. The [configuration reference](/reference/configuration#backlog-pages) describes saved views.

## Inspect the board

```bash
fno backlog board
```

The board groups work as Just finished, In progress, and On deck. It reads local graph, PR-cache, and Git evidence.

This command does not fetch current GitHub checks. Inspect the PR itself before treating a cached board state as delivery proof.

## Record and edit work

Create a small task from your project terminal:

```bash
fno backlog idea "Practice documentation task" --difficulty low --json
```

The JSON receipt names its ID. If the command offers to fold it into existing work, read that choice before creating another node.

Replace `<TASK_ID>` below with the ID from that receipt:

```bash
fno backlog get <TASK_ID>
fno backlog update <TASK_ID> priority=p3
```

The first command prints the node. The second prints `Updated` and the node ID. Read its notes as well as the original description.

Edit existing work with `fno backlog update`. Creating another idea with the same title does not edit the old node.

Priorities run from `p0` to `p3`. Difficulty describes the work itself: `low`, `medium`, or `high`.

## Choose a view

| View | Use it for | Freshness |
| --- | --- | --- |
| Terminal board | A quick local summary | Reads local evidence when invoked |
| Mux Backlog tab | Work alongside running agents | Uses the local board projection |
| Saved HTML | Open or share a snapshot | Reflects its last render |
| Mux web backlog | Inspect the served board in a browser | Depends on the serving process and refresh |

Saved pages use `backlog.render_targets`. The daemon also maintains a local board copy at `~/.fno/cache/pages/graph.html`.

The mux is fno's terminal workspace for watching agents. Its Backlog tab and browser view show projections of the same task graph.

An HTML file opened from disk is a snapshot. It is not a live database editor. Check its render time before acting on its contents.

## Respect ownership

Before starting another worker, inspect ownership:

```bash
fno agents claim status node:<TASK_ID> --json
```

Use the same `<TASK_ID>` as above. `live` or `suspect` is not permission to start a competing owner.

A `free` claim means no holder was established by that reading. Check roster coverage in the same JSON before concluding nobody is working.

`roster_workers` lists matching workers found by the cross-check. `roster_coverage: degraded` means the roster could not be fully resolved.

If matching workers exist or coverage is degraded, inspect those sessions before assigning another owner. An incomplete check is not proof of absence.

If this task needs another task's result, record its dependency:

```bash
fno backlog update <TASK_ID> blocked_by+=<PREREQUISITE_ID>
```

Replace `<PREREQUISITE_ID>` with an existing node's ID. A prerequisite with `status: done` or a recorded `completed_at` no longer blocks that selection.

Eligibility does not promise an immediate launch. Capacity, ownership, and other dispatch policies still apply.

Do not use priority as a substitute for a dependency. Leave practice tasks clearly labeled rather than assigning them to a live worker.

For all editable fields and lifecycle moves, read the installed help:

```bash
fno backlog update --help
```
