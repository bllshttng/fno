title: "Review and ship"
description: "Inspect the current PR head, CI, review findings, and merge policy."
---

Target runs the delivery loop for you. After it reports a PR, inspect the evidence described here.

## Before you begin

Use the [quickstart](/quickstart) to create a PR, or open an existing PR for work you own.

The [CLI reference](/reference/cli#pull-request-status) describes the CI reading. [Completion concepts](/concepts/completion) explain the other evidence.

## Read the proposed change

Open the PR URL. Confirm the target repository and base branch, then read the diff.

Check that the current head contains the intended change. Evidence from an earlier commit does not automatically cover a later fix.

## Check CI

Use `fno do pr status` with your PR number, from the corresponding repository. It reports green, red, pending, or unknown.

A green CI verdict alone does not prove review is complete. A failed status read is missing evidence, not success.

## Check review

Read the review comments and the response to each blocking finding. Confirm whether a finding was fixed or explicitly left unresolved.

The `fno:review` workflow runs inline in the coding session. Its attestation records the reviewed head.

An attestation is the review record tied to a commit. Read the review comment in the PR conversation after the held local review is published.

If that record names an earlier head, check whether current review coverage still applies before merging.

When driving delivery manually, use `fno:ship pr create` after review and `fno:ship pr check` for configured external review.

These names identify harness workflows. The [harness reference](/reference/harnesses) shows the prompt prefix for each harness.

## Check merge authority

Read the effective [automatic-merge policy](/reference/configuration#automatic-merging). If your configuration authorizes it, a target can merge automatically.

If automatic merging is disabled, use GitHub's merge control on the PR after reviewing the evidence. Respect repository branch protections.

An open PR and a merged PR are different outcomes.

After a merge, `fno:ship pr merged` performs the project's post-merge workflow. Publishing or deployment can still require separate work.
